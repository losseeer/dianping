## 一、分布式登录模块

> 涉及文件：`UserServiceImpl`、`RefreshTokenInterceptor`、`LoginInterceptor`、`UserHolder`、`MvcConfig`

### 亮点1：Redis + Token 替代 Session 实现集群登录

| 项目设计亮点 | 八股知识 |
|---|---|
| 用 Redis 存储用户信息，Token 作为 Key，解决了集群环境下的 Session 共享问题 | **Session 共享方案对比**：Session 复制（延迟+带宽）、Session 粘粘（负载不均）、Redis 集中存储（本项目方案） |
| Token 用 UUID 生成，不带任何业务信息 | **Token vs JWT 的选型**：JWT 无状态但无法主动失效；Redis+Token 可以随时让用户下线，安全性更高 |
| 用户信息用 Redis Hash 结构存储（`HashOperations`） | **Redis Hash vs String(JSON)**：Hash 可单独修改字段，内存占用更少（ziplist 编码）；String+JSON 更通用，实际工作中更常见 |

**面试官可能这样问：**
1. 为什么不用 JWT？JWT 有什么缺点？
2. 集群环境下 Session 怎么共享？你们怎么做的？
3. Token 存 Redis 的 Key 怎么设计的？过期时间多少？
4. 如果 Redis 挂了，用户是不是全掉线了？怎么办？

### 亮点2：双层拦截器架构（Token刷新 + 登录校验分离）

| 项目设计亮点 | 八股知识 |
|---|---|
| 第一层 `RefreshTokenInterceptor`（order=0）拦截所有路径，负责 Token 解析和有效期刷新 | **拦截器执行顺序**：order 值越小优先级越高，preHandle 正序执行，afterCompletion 逆序执行（洋葱模型） |
| 第二层 `LoginInterceptor`（order=1）只拦截需要登录的路径，从 ThreadLocal 取用户校验 | **拦截器 vs 过滤器（Filter）**：Filter 是 Servlet 规范在 DispatcherServlet 之前；Interceptor 是 Spring MVC 在 Controller 之前；Interceptor 可注入 Spring Bean |
| Token 刷新策略：每次请求刷新 30 分钟有效期，用户活跃期间不掉线 | **Token 续期策略**：类似 Session 的滑动过期，活跃就续期，不活跃就自动过期 |

**面试官可能这样问：**
1. 为什么要两层拦截器？一层不行吗？
2. 拦截器和过滤器有什么区别？你选哪个？为什么？
3. 拦截器的 preHandle、postHandle、afterCompletion 分别什么时候执行？
4. 如果用户一直在浏览但 30 分钟没操作，会发生什么？

### 亮点3：ThreadLocal 传递用户信息

| 项目设计亮点 | 八股知识 |
|---|---|
| 拦截器解析 Token 后将用户信息存入 `ThreadLocal<UserDTO>`，后续 Service 直接 `UserHolder.getUser()` 获取 | **ThreadLocal 原理**：每个 Thread 内部有一个 ThreadLocalMap，key 是 ThreadLocal 对象（弱引用），value 是变量值（强引用） |
| 在 `afterCompletion` 中应该调用 `removeUser()` 清理 | **ThreadLocal 内存泄漏**：key 是弱引用会被 GC 回收变成 null，但 value 是强引用不会回收 → 内存泄漏；Tomcat 线程池中线程复用，不 remove 会导致数据错乱 |
| 用户信息在请求线程内全局可取，无需方法参数传递 | **ThreadLocal 应用场景**：数据库连接管理、事务管理（同一事务用同一连接）、SimpleDateFormat 线程安全、全链路 traceId 传递 |

**面试官可能这样问：**
1. ThreadLocal 的原理是什么？画一下它的内部结构。
2. ThreadLocal 为什么会内存泄漏？怎么避免？
3. ThreadLocalMap 的 key 为什么要设计成弱引用？
4. 线程池中使用 ThreadLocal 有什么注意事项？
5. ThreadLocal 和 Synchronized 有什么区别？

## 二、缓存体系模块

> 涉及文件：`CacheClient`、`ShopServiceImpl`

### 亮点4：Cache Aside 旁路缓存模式

| 项目设计亮点 | 八股知识 |
|---|---|
| 读：先查缓存，miss 再查数据库并回填缓存 | **Cache Aside 模式**：应用层维护缓存，读先缓存后数据库，写先更新数据库再删除缓存 |
| 写：先更新数据库，再删除缓存（不是更新缓存） | **为什么删除而不是更新缓存**：并发写时更新缓存可能数据不一致；删除是懒加载，用到了才查；减少写操作 |
| 缓存空值防止穿透，随机 TTL 防止雪崩 | **缓存一致性策略**：延迟双删、Canal 监听 binlog、消息队列保证最终一致性 |

**面试官可能这样问：**
1. 先更新数据库还是先更新缓存？为什么？
2. 先删缓存再更新数据库有什么问题？延迟双删怎么做的？
3. 你了解哪些缓存一致性方案？Canal 监听 binlog 的原理是什么？
4. Cache Aside 和 Read/Write Through 有什么区别？

### 亮点5：缓存穿透防护（缓存空值）

| 项目设计亮点 | 八股知识 |
|---|---|
| 数据库查不到的数据，缓存一个空字符串 `""`，设置 2 分钟短 TTL | **缓存穿透定义**：请求的数据在缓存和数据库中都不存在，每次请求都打到数据库 |
| 空值设置较短过期时间，避免长期占用内存 | **布隆过滤器（Bloom Filter）**：位图 + 多个哈希函数，判断"一定不存在"或"可能存在"；有误判率但内存占用极小 |

**面试官可能这样问：**
1. 什么是缓存穿透？和缓存击穿、缓存雪崩有什么区别？
2. 缓存空值有什么缺点？布隆过滤器能完全替代吗？
3. 布隆过滤器的原理是什么？为什么会有误判？能删除元素吗？
4. 如果有人用大量不存在的 ID 恶意请求，你怎么防？

### 亮点6：缓存击穿防护（互斥锁 + 逻辑过期双方案）

| 项目设计亮点 | 八股知识 |
|---|---|
| 方案一：互斥锁（`setnx`），缓存 miss 时只有一个线程查数据库重建缓存 | **互斥锁方案**：`SET key value NX EX 10`，获取锁的线程重建缓存，其他线程等待或返回旧数据 |
| 方案二：逻辑过期，value 中存过期时间字段，Redis 永不过期，过期后后台线程异步重建 | **逻辑过期方案**：用户永远能拿到数据（可能旧一点），后台线程偷偷重建，用空间换可用性 |
| 用 `tryLock` 获取锁，`finally` 中释放锁 | **两种方案对比**：互斥锁一致性高但需等待；逻辑过期性能好但有短暂不一致 |

**面试官可能这样问：**
1. 缓存击穿和缓存穿透有什么区别？
2. 互斥锁和逻辑过期你选哪个？为什么？
3. 逻辑过期方案中，缓存重建时如果线程池满了怎么办？
4. 互斥锁获取失败后，是等待重试还是返回错误？怎么实现的？
5. 逻辑过期的 Double Check 是什么？为什么需要？

### 亮点7：缓存雪崩防护

| 项目设计亮点 | 八股知识 |
|---|---|
| 给缓存 TTL 添加随机偏移，避免大量 key 同时过期 | **缓存雪崩定义**：大量 key 在同一时间过期，或 Redis 宕机，所有请求打到数据库 |
| 实际项目中还应做 Redis 集群高可用 | **雪崩解决方案**：随机过期时间、Redis 集群（主从+哨兵）、多级缓存（本地缓存 + Redis）、服务降级 |

**面试官可能这样问：**
1. 缓存雪崩和缓存击穿的区别是什么？
2. 如果 Redis 整个挂了怎么办？你们的高可用方案是什么？
3. 你了解 Redis 的哨兵模式吗？主从切换的过程是什么？

## 三、秒杀系统模块

> 涉及文件：`VoucherOrderServiceImpl`、`SeckillVoucherListener`、`QueueConfig`、`seckill.lua`

### 亮点8：Lua 脚本保证 Redis 操作原子性

| 项目设计亮点 | 八股知识 |
|---|---|
| 用 Lua 脚本一次性完成"判断库存→判断一人一单→扣库存→记录用户→发消息" | **Redis 单线程模型**：Redis 命令是单线程串行执行的，单条命令原子但多条命令不保证原子性 |
| Lua 脚本中判断库存用 `get`、扣库存用 `incrby`、判断一人一单用 `sismember` | **Lua 脚本原子性**：Redis 将整个 Lua 脚本当作一个整体执行，期间不会被其他命令打断 |
| 脚本返回值约定：0=成功，1=库存不足，2=重复下单 | **Lua 脚本的优势**：原子性、减少网络 IO（一次调用完成多步操作）、可复用 |

**面试官可能这样问：**

### 亮点9：乐观锁（CAS）防止超卖

| 项目设计亮点 | 八股知识 |
|---|---|
| 扣减库存时 SQL 加 `where stock > 0` 条件，利用 MySQL 行锁实现乐观锁 | **超卖问题**：多个线程同时读到 stock=1，都判断 >0，都扣减，结果 stock=-1 |
| 不用版本号机制，直接用库存值本身做条件判断 | **乐观锁 vs 悲观锁**：悲观锁 `select ... for update` 串行化，性能差；乐观锁 CAS 无锁竞争，性能好但高并发下成功率低 |
| `update set stock=stock-1 where id=? and stock > 0` | **CAS（Compare And Swap）**：比较并交换，比较当前值是否等于预期值，相等则更新 |

**面试官可能这样问：**
1. 超卖是怎么产生的？画一下并发场景。
2. 乐观锁和悲观锁的区别？各自适合什么场景？

### 亮点10：Redis + RabbitMQ 异步下单

| 项目设计亮点 | 八股知识 |
|---|---|
| Lua 脚本预检通过后，立即返回订单号，RabbitMQ 异步消费写数据库 | **异步下单架构**：Redis 预检（毫秒级）→ MQ 投递 → 消费者异步创建订单，用户无需等待数据库写入 |

### 亮点11：Redis 分布式 ID 生成器

## 四、分布式锁模块

> 涉及文件：`SimpleRedisLock`、`RedissonConfig`、`VoucherOrderServiceImpl`

### 亮点12：自研 Redis 分布式锁的演进过程

| 项目设计亮点 | 八股知识 |
|---|---|
| 第一版：`setnx key value`，有死锁问题（服务宕机锁不释放） | **死锁问题**：获取锁后服务宕机，锁永远不释放，其他线程永远拿不到锁 |
| 第二版：`setnx + expire`，不是原子操作 | **原子性问题**：setnx 后 expire 前宕机，锁没有过期时间变成死锁 |
| 第三版：`set key value nx ex seconds`，原子操作 | **Redis 2.6.12+ SET NX EX**：一步完成 set+expire，原子性有保障 |
| 第四版：value 存 UUID+线程ID，释放锁时先判断再删除 | **误删锁问题**：线程 A 锁过期后线程 B 获取锁，线程 A 执行完把 B 的锁删了 |
| 第五版：用 Lua 脚本释放锁，保证"判断+删除"原子性 | **Lua 脚本释放锁**：`if redis.call('get',KEYS[1])==ARGV[1] then return redis.call('del',KEYS[1]) else return 0 end` |
| 最终方案：切换到 Redisson，解决可重入、续期、主从一致等问题 | **Redisson 原理**：Hash 结构存重入次数、看门狗续期、multiLock 红锁解决主从一致 |

**面试官可能这样问：**
1. 分布式锁的实现方案有哪些？各有什么优缺点？
2. 你自己实现的分布式锁有什么问题？怎么一步步改进的？
3. 为什么释放锁要用 Lua 脚本？
4. Redisson 的可重入锁怎么实现的？画一下 Hash 结构。
5. Redisson 的看门狗机制是什么？如果不指定 leaseTime 会怎样？
6. Redis 主从切换导致锁丢失怎么办？Redlock 了解吗？
7. 分布式锁用 Zookeeper 和 Redis 有什么区别？

### 亮点13：锁的粒度设计

| 项目设计亮点 | 八股知识 |
|---|---|
| 一人一单的锁粒度是 `userId` 而不是 `voucherId` | **锁粒度原则**：锁的粒度越小越好，只锁必须互斥的资源；锁 userId 保证同用户串行，不同用户并行 |
| 秒杀预检用 Lua 脚本天然互斥，不需要额外加锁 | **无锁设计**：Lua 脚本利用 Redis 单线程特性天然互斥，比分布式锁性能更好 |

**面试官可能这样问：**
1. 你的锁加在 userId 上还是 voucherId 上？为什么？
2. 如果锁 voucherId 会怎样？有什么问题？
3. 锁的粒度怎么决定？粗一点和细一点各有什么影响？
4. 一人一单用 Lua 脚本和分布式锁各有什么优缺点？

### 亮点16：BitMap 实现用户签到

| 项目设计亮点 | 八股知识 |

### B. Redis 深度问题

| 问题 | 关联模块 | 核心八股 |
|---|---|---|
| Redis 为什么快？ | 全局 | 单线程避免上下文切换、纯内存操作、IO 多路复用（epoll）、高效数据结构 |
| Redis 6.0 多线程是什么？ | 全局 | IO 多线程（网络读写），命令执行仍单线程；解决网络 IO 瓶颈而非计算瓶颈 |
| Redis 的持久化方案？ | 全局 | RDB（快照，恢复快但可能丢数据）、AOF（追加日志，数据安全但文件大）、混合持久化（RDB+AOF） |
| Redis 缓存淘汰策略？ | 缓存 | 8种：noeviction、allkeys-lru、allkeys-lfu、volatile-lru、volatile-lfu、allkeys-random、volatile-random、volatile-ttl |
| Redis 的大 Key 问题？ | 缓存 | 单个 value 超过 10KB 为大 Key；删除大 Key 会阻塞主线程（del 是同步操作）；用 unlink 异步删除 |
| Redis 的热点 Key 问题？ | 缓存 | 热点 Key 集中访问导致单节点压力；解决方案：本地缓存、Key 分散（加随机后缀）、读写分离 |

### C. 消息队列深度问题

| 问题 | 关联模块 | 核心八股 |
|---|---|---|
| RabbitMQ 怎么保证消息不丢失？ | 秒杀/MQ | 生产者确认（confirm）、队列持久化（durable=true）、消费者手动 ACK |
| RabbitMQ 怎么保证消息有序？ | 秒杀/MQ | 单队列单消费者；或按业务 Key 路由到同一队列 |
| 死信队列是什么？什么场景用？ | 延迟取消 | 消息被拒绝/过期/队列满 → 进入死信交换机 → 死信队列；用于延迟队列、重试机制 |
| RabbitMQ 和 Kafka 有什么区别？选型？ | 全局 | RabbitMQ：可靠性高、功能丰富、吞吐量万级；Kafka：高吞吐（百万级）、日志场景、顺序消息 |

### D. 数据库深度问题

| 问题 | 关联模块 | 核心八股 |
|---|---|---|
| MySQL 的隔离级别有哪些？ | 全局 | 读未提交、读已提交、可重复读（MySQL默认）、串行化 |
| MySQL 的 MVCC 是什么？ | 全局 | 多版本并发控制，通过 undo log + read view 实现，读不加锁提高并发 |
| MySQL 的索引为什么用 B+ 树？ | 全局 | B+ 树非叶子节点不存数据，扇出更大，层数更少；叶子节点链表相连，范围查询高效 |
| 你用乐观锁更新库存，MySQL 怎么保证不超卖？ | 秒杀 | `update ... where stock > 0` 利用行锁 + 条件判断，MySQL 的行锁是排他锁（X锁） |

### E. Spring 深度问题

| 问题 | 关联模块 | 核心八股 |
|---|---|---|
| Spring AOP 的实现原理？ | 限流/熔断 | JDK 动态代理（接口）和 CGLIB（类继承）；Spring 默认有接口用 JDK，没接口用 CGLIB |
| Spring 事务什么时候会失效？ | 秒杀 | 同类方法调用（this调用绕过代理）、方法非 public、异常被 catch 吃掉、数据库引擎不支持事务、多线程 |
| `@Transactional` 的传播行为？ | 秒杀 | REQUIRED（默认，有就加入）、REQUIRES_NEW（新建）、NESTED（嵌套）等 7 种 |
| Bean 的循环依赖怎么解决？ | 支付模块 | 三级缓存：singletonObjects（成品）、earlySingletonObjects（半成品）、singletonFactories（工厂）；用 `@Lazy` 打破循环 |
| Spring Boot 自动配置原理？ | 全局 | `@SpringBootApplication` → `@EnableAutoConfiguration` → SPI 加载 `META-INF/spring.factories` → 条件注解过滤 |
