# 第〇部分:开场白(必背)

## 0.1 项目一句话(30 秒电梯演讲)

> 我做了一个点评类平台,简历上拆成两个子项目:**快评**和**推荐 Agent**。快评是"后端 + AI 摘要服务":后端用 Redis+Lua+MQ 做秒杀、多级缓存和支付状态机,AI 服务把一家店几百条评论并发地做情感分析,聚合成好评率、优缺点 Top3 和一段综合建议。推荐 Agent 是一个 LangGraph 状态机:带三层记忆(会话压缩/用户偏好/全局经验库)、人在环(HITL)中断恢复、以及一条"轨迹→信号→蒸馏→经验回注"的自进化闭环,并有 80 个用例的评估集和消融实验支撑。

## 0.2 一分钟版本

> 整个系统四个服务:**Java 后端(8081,主业务)+ Agent1(8001,快评摘要)+ Agent2(8002,推荐对话)+ Vue 前端**。
> 后端核心是交易链路:秒杀用 Lua 脚本把"判库存、判一人一单、扣减、写预订单、发 Stream 消息"做成一个原子操作,消费者异步落库,RabbitMQ 死信队列做 30 分钟超时取消,本地事件表(Outbox)+ publisher-confirm 保证消息最终不丢;支付侧有六态状态机、PayLog 流水和 HMAC-SHA256 验签。缓存侧做了穿透(空值缓存)和击穿(逻辑过期+异步重建)两类防护。Agent1 是线性五步管线:采集→批量情感分析→纯代码统计→LLM 综合建议→结构化输出,Redis 缓存 30 分钟。Agent2 是八节点 LangGraph 图,evaluate/replan 全部规则化零 LLM,LLM 只花在 plan 和 generate 两个节点上;有令牌桶+信号量+退避重试的四层 LLM 防护和 jsonl 全链路观测。
> 我对两条链路都做了压测/评估:后端查询 100 并发 QPS 3306、P95 17.6ms,秒杀 30 并发 QPS 803 且零超卖;Agent2 有 60 单轮+20 多轮用例的评估集,做过记忆/经验库/重规划三个维度的消融。

## 0.3 三分钟版本(白板讲架构)

画四层:

```
Vue 前端 ──┬─ /api ──────→ Java 后端(8081)── MySQL / Redis / RabbitMQ / ES
           ├─ /agent1 ───→ Agent1 快评(8001)──→ 反向调 Java API 拿数据 ──→ LLM
           └─ /agent2 ───→ Agent2 推荐(8002)──→ 调 Java 搜索/详情 + 调 Agent1 ──→ LLM
                                                Redis(记忆/轨迹/队列) + MySQL(偏好/经验/会话) + ChromaDB(经验向量检索)
```

讲的时候按"请求走一遍"的顺序:
1. 秒杀请求:Controller 令牌桶(50 qps)→ Lua 原子七步 → 秒回订单号 → Redis Stream 异步落库 → 死信队列 30min 超时取消 → Outbox 兜底一切跨系统写。
2. 快评请求:前端直连 Agent1 → 拉 Java API 分页取评论(上限 250)→ 采样(top150+bottom30)→ batch=5 并发结构化抽取 → 纯代码统计 → LLM 综合 → 缓存 30min。
3. 推荐对话:load_memory → plan(LLM,注入三段上下文)→ execute(5 个工具调 Java/Agent1)→ evaluate(纯规则四路分叉)→ generate(LLM 硬规则选 Top5)→ log_trajectory → 异步蒸馏进 Playbook。

## 0.4 简历边界(防被抓包)

- 前端是**通过 Vite 代理直连 Agent1/Agent2** 的,Java 后端不调用 Agent——被问"后端怎么整合 AI"就照实说"AI 服务独立部署、前端网关直连,后端只提供数据 API",这是微服务边界清晰的体现,不是缺点。
- MQ 用的是 **RabbitMQ**(延迟取消)+ **Redis Stream**(秒杀削峰),不要说成 RocketMQ/Kafka。
- Redis 统计功能实际实现的是 **BitMap 签到**,没有 HyperLogLog(可作为"可扩展方案"谈)。
- LLM 默认配置 `gpt-4o-mini` 走 OpenAI 兼容接口,实测用的是 DeepSeek;简历上写"OpenAI 兼容协议接入,模型可切换"最稳。
- 压测环境是本机,数字讲"量级和相对差异",不吹绝对值。

# 第壹部分:项目深挖——快评(后端 + Agent1)

## A. 秒杀链路(最高频考点)

### Q1:讲一下你的秒杀是怎么做的?

【答】分五层讲:

1. **限流层**:Controller 上 `@RateLimit(qps=50)`(自定义 AOP + Guava RateLimiter),超出直接拒绝,保护后面所有链路。
2. **原子预扣层**:核心是一段 Lua 脚本(`resources/seckill.lua`),在 Redis 单线程里原子完成七步:①查库存 key,不存在返回 -1;②库存 ≤0 返回 1;③`SISMEMBER seckill:order:{voucherId}` 判一人一单,命中返回 2;④`INCRBY` 扣库存;⑤`SADD` 记录用户;⑥写一个 10 分钟 TTL 的**预订单 JSON**(解决异步落库窗口期"订单不存在");⑦写用户维度 pending ZSet 索引;最后 `XADD stream.orders` 把订单事件发进 Redis Stream——**扣库存和发消息在同一个脚本里原子提交**,不存在"扣了库存但消息丢了"的窗口。
3. **异步落库层**:Lua 返回 0 就立即把订单号返给用户。消费者线程 `XREADGROUP ... COUNT 10 BLOCK 2000` 拉消息,在 Redisson 锁(`lock:order:{userId}:{voucherId}`)+ `@Transactional` 里落库:主键存在性检查幂等 → count 有效状态订单兜底一人一单 → `stock=stock-1 where stock>0` 乐观锁扣 DB 库存 → 唯一索引 `uk_active_user_voucher` 兜底,捕获 `DuplicateKeyException` 转成业务结果。
4. **超时取消层**:落库成功后发 RabbitMQ 消息到 TTL=30 分钟的延迟队列,死信转到取消队列,消费者把仍处 UNPAID 的订单条件更新为 CANCELLED、回补 DB 库存、再通过 Outbox 发 Redis 补偿事件回补 Redis 库存。
5. **兜底层**:本地事件表 Outbox + publisher-confirm,保证"DB 状态变更了但 MQ 发失败"最终一定重发。

### Q2:为什么用 Lua 脚本?不用行不行?

【答】判断+扣减+写 Set+发消息是**多个 Redis 命令**,分开执行的话并发下会出现:两个请求同时读到 stock=1 都通过校验(超卖)、或者扣完库存进程崩溃消息没发出(少卖)。Lua 脚本在 Redis 单线程里整体执行,天然串行原子,等价于把"检查-扣减-记录"变成一个临界区。代价是脚本里不能有慢逻辑,我的脚本全是 O(1)/O(logN) 命令(GET/INCRBY/SISMEMBER/SADD/XADD)。

追问"为什么不用分布式锁":锁能保证互斥但每次抢锁释放是两次额外网络往返,高并发下大量线程阻塞在锁上;Lua 把临界区搬到 Redis 进程内,一次网络往返完成,吞吐高一个量级。

### Q3:一人一单是怎么保证的?有几层防线?

【答】三层,层层递进:
1. **Redis 层**:`SISMEMBER seckill:order:{voucherId} userId` 在 Lua 里 O(1) 判重,拦截 90%+ 的重复请求(压测:10 并发同人只有 1 单成功)。
2. **DB 校验层**:落库前 count 该用户该券处于 UNPAID/PAID/VERIFIED/REFUNDING 四种"仍占资格"状态的订单数。这里有个我踩过的坑:最初写成 count 所有状态,导致**取消/退款后无法重新秒杀**——后来改为只统计四种活跃状态,CANCELLED/REFUNDED 终态不算数。
3. **DB 约束层(最终防线)**:`UNIQUE uk_active_user_voucher(user_id, voucher_id, active_flag)`,有效单 active_flag=1,终态置 NULL 让唯一约束放行,支持"取消后再买"。并发插入撞唯一键抛 `DuplicateKeyException`,捕获后回滚并触发 Redis 资格释放。

为什么三层都要:Redis 层挡流量、DB 校验层挡业务漏网、唯一索引挡一切代码 bug——**约束比代码更可信**。

### Q4:Redis 扣完库存直接返回订单号,那 MySQL 落库失败怎么办?

【答】分场景:
- **重复消费/重复单**(ACTIVE_ORDER_EXISTS):调用 `releaseRejectedReservation` 回滚——恢复 Redis 库存、按需释放一人一单资格。
- **DB 库存不足**(OUT_OF_STOCK,说明 Redis 领先于 MySQL):**不**回滚 Redis,保留预扣让缓存库存向 DB 收敛,避免超卖。
- **消费过程异常**:消息留在 Stream 的 PENDING 列表。我的消费者有三层可靠性:①正常 `XACK`;②每轮重读**自己的** PENDING(单轮上限 200 条);③`XPENDING + XCLAIM minIdleTime=30s` **认领崩溃实例遗留的消息**——这是 Stream 相比简单队列的关键优势,消费位置和确认状态都在 broker 侧。
- 消费者本身幂等(先按订单号查存在即返回 ALREADY_PROCESSED),所以重试是安全的。

### Q5:为什么削峰用 Redis Stream,延迟取消却用 RabbitMQ?为什么不统一?

【答】按需选型:
- 秒杀削峰要的是**极高写入吞吐 + 消费位置管理**,Redis Stream 与预扣在同一实例内,Lua 里直接 XADD 零额外网络开销,还能 XCLAIM 做故障转移,所以选它。
- 超时取消要的是**延迟投递**,需要成熟 TTL+死信机制,Redis 原生没有(过期监听不可靠),所以用 RabbitMQ 死信队列:延迟队列 `x-message-ttl=1800000` + `x-dead-letter-exchange`,到期死信进取消队列。
- 另一个细节:消息发出到落库成功有异步延迟,我**按已流逝时间动态扣减 TTL**(`remaining = 30min - (now - createTime)`),保证"下单起 30 分钟"而不是"落库起 30 分钟"。

被问"引入两种 MQ 会不会太重":承认这是学习项目的取舍,生产上如果已有 RabbitMQ 集群,可以统一用 RabbitMQ(延迟用插件)或者都用 Stream,我两边都写过所以能对比选型。

### Q6:讲讲你的分布式锁。为什么消费端用 Redisson?

【答】项目里有三把锁,分别对应三个场景:
1. **消费端防重复消费**:`redissonClient.getLock("lock:order:"+userId+":"+voucherId)`,`lock()` 阻塞式且不指定 leaseTime——此时**看门狗(watchdog)生效**,默认 30 秒租期、每 10 秒续期,落库再慢锁也不会过期;释放前 `isHeldByCurrentThread()` 检查防解别人的锁。粒度是 用户+券,不同用户互不阻塞。
2. **手写 SimpleRedisLock**(教学对比):`setIfAbsent(key, UUID-threadId, timeoutSec)` 加锁,释放用 **unlock.lua** 做"值相等才删"的原子校验——防止 A 超时锁自动过期后,B 拿到锁,A 回来把 B 的锁删了。这里我发现一个真实的跨平台坑:代码加载的是 `unlock.lua`,资源文件实际叫 `unLock.lua`,Windows 大小写不敏感能跑,**Linux 上会 NPE**,这类问题在容器化部署时很典型。
3. **缓存重建锁**:`setIfAbsent("lock:shop:"+id, 10s)`,抢不到说明别人在重建,直接返回旧数据。

追问 Redisson 原理:看门狗通过定时任务(内部时间轮)每 lockWatchdogTimeout/3 续期;可重入通过 Hash 结构(field=线程标识,value=重入次数)。追问 RedLock:多主节点多数派加锁,但有 GC/时钟漂移争议(Martin Kleppmann vs Antirez 之争),我的场景单 Redis + 业务幂等兜底足够。

### Q7:消息会不会丢?你的 Outbox 具体怎么做的?

【答】先说结论:三段各有手段——**发送端** publisher-confirm(`CorrelationData.getFuture().get(5s)` 同步等 ack,未路由触发 returns 回调)、**broker** 持久化交换机/队列/消息、**消费端** 手动 ack + Stream PENDING 重投。

但有一个更隐蔽的缺口:**"DB 事务提交成功"和"MQ 发送成功"无法原子**。发 MQ 成功后事务回滚=幽灵消息;事务成功后发 MQ 前进程崩溃=消息丢失。我用**本地事件表(Outbox)**解:业务事务里同库 insert 一条 `tb_transaction_outbox`(event_key 唯一约束防重),后台任务每 1 秒扫 `status=0` 的最多 50 条,**CAS 抢占**(`update set status=2 where id=? and status=0`,多实例部署也不重复发),发送成功置 1,失败按 `min(300s, 2^retry)` 指数退避回滚到 0,卡在"发送中"超 1 分钟的重置。事件类型有 PAY_NOTIFY / REFUND / REDIS_COMPENSATION 三种。

Redis 补偿还有一个细节:用 `TransactionSynchronizationManager.afterCommit` 保证**事务提交后**才去动 Redis,避免"事务还没提交,Redis 先恢复了,事务又回滚"的不一致。

### Q8:订单 ID 为什么不 用自增?

【答】`RedisIdWorker`:全局 ID = (时间戳相对 2022 纪元的秒) << 32 | Redis `INCR` 序列号。要点:①订单号要暴露给前端,自增会泄露单量(商业敏感);②分库分表下自增会冲突;③INCR 的 key 按**天分片**(`icr:order:yyyy:MM:dd`),避免单 key 无限增长,32 位序列号一天 40 亿上限足够。对比雪花:雪花依赖时钟,回拨会重复;Redis 方案时钟只影响高位可容忍。

## B. 支付与订单状态机

### Q9:订单状态机是怎么设计的?

【答】六态:`UNPAID → PAID → VERIFIED(核销)/ REFUNDING → REFUNDED`,`UNPAID → CANCELLED`;VERIFIED/CANCELLED/REFUNDED 是终态。`OrderStatus.canTransitionTo()` 集中定义合法迁移,支付入口先校验状态机再操作。**所有状态变更都是条件 UPDATE**(如 `set status=PAID where id=? and status=UNPAID`),数据库比较交换(CAS):并发场景下"支付成功"和"超时取消"只有一方能更新成功,另一方更新 0 行走补偿——这是无锁幂等的根基。

### Q10:支付幂等怎么保证?回调怎么验签?

【答】幂等四件套:
1. **PayLog 流水表**:`uk_pending_order(order_id, pending_flag)` 唯一约束——同一订单同时只能有一笔待支付流水;`uk_trade_no` 保证交易号唯一。
2. 回调按 `order_id + trade_no` **精确匹配流水**(不取最新一笔),再**比对金额**(回调金额 ≠ 下单快照金额即拒绝)。
3. PayLog status=2(成功)直接幂等短路返回。
4. 订单状态条件更新 CAS。

验签:`POST /pay/notify` 请求头带 `X-Payment-Signature`,服务端用配置的 secret 对 `"PAY\n{tradeNo}\n{orderId}\n{amount}"` 做 **HMAC-SHA256**,要求 64 位 hex,用 `MessageDigest.isEqual` **常量时间比较**防时序攻击。secret 走环境变量,**默认空=所有公网回调直接拒绝**(fail-safe 默认关闭)。

**迟到支付**(回调到达时订单已被超时取消):流水照常置成功,但立刻发 REFUND 消息**原路退回**——钱不能吞,状态要一致。

### Q11:模拟支付是怎么做的?余额支付为什么同步回调?

【答】本地没有真实扫码渠道,SDK 是 mock 的(`https://pay.mock/{渠道}/qrcode?tradeNo=..`)。这里有个我主动修的体验 bug:微信/支付宝走"二维码+异步回调"没问题,但**余额支付**弹二维码很荒谬——余额就在我系统里,不需要出系统。所以 BALANCE 类型在支付事务内**同步走一遍相同的 handlePayNotify 回调逻辑**(通过 selfProxy 代理调用),复用同一套幂等/验签/状态机代码。诚实说明:当前 mock 没有真实扣减余额账户,这是 demo 边界。

### Q12:@Transactional 什么时候会失效?你项目里怎么踩的?

【答】**自调用**:`this.createVoucherOrder()` 走的是原始对象不是代理,事务注解直接失效。标准解法是 `AopContext.currentProxy()`,但它要求 `exposeProxy=true` 且当前线程有代理上下文——**我的消费者是自建的 daemon 线程,不是 HTTP 线程,AopContext 拿不到**。最终方案:`@Lazy private VoucherOrderServiceImpl selfProxy;` 自注入拿到代理引用。顺带一提 PaymentServiceImpl 和 VoucherOrderServiceImpl 存在循环依赖,也是用双向 `@Lazy` 打破的——这个可以引申到 Spring 三级缓存(见八股 Q3.4.4)。

## C. 缓存

### Q13:缓存穿透怎么处理的?

【答】`CacheClient.queryWithPassThrough`:查 Redis 命中**空字符串**直接返回 null;未命中查 DB,DB 也没有就 `set(key, "", 2, MINUTES)` 缓存空值。TTL 故意设短(2 分钟),平衡"挡穿透"和"新数据写入后不一致窗口"。
被问布隆过滤器:方案对比我写在代码注释里——布隆能省内存但有不识别删除、误判率、维护成本,点评场景恶意攻击的 key 空间近乎无限,空值缓存更简单有效;若是超高 QPS 的固定 key 空间(如商品 ID),布隆更合适。

### Q14:缓存击穿呢?讲讲逻辑过期方案的细节。

【答】热点 key 过期瞬间大量请求打到 DB。我实现了**逻辑过期**:缓存值包一层 `RedisData{expireTime, data}`,**不设物理 TTL**——key 永远存在,不存在"过期瞬间"。查询时发现逻辑过期 → `setIfAbsent("lock:shop:"+id, 10s)` 抢重建锁 → 抢到的线程提交到 `CACHE_REBUILD_EXECUTOR`(固定 10 线程)异步查库回填 → **所有请求(包括抢到锁的)立即返回旧数据**。一致性换可用性,适合秒杀商品这种"短暂旧数据可接受"的场景。
对比互斥锁版(我也保留实现了):互斥保证强一致但重建期间请求阻塞;逻辑过期线程不等待但有旧数据窗口。
主动坦白的坑:①抢到锁后**缺 Double Check**,理论上可能重复重建(幂等无害但浪费);②finally 里 unLock 传错了 key(应该解 lockKey)——这两个都是我 review 时发现的,修复很简单,但**面试主动讲"我发现了什么"比"我写对了什么"更有说服力**。

### Q15:缓存和数据库一致性怎么保证?

【答】**Cache Aside:先更新 DB,再删缓存**(updateShop 在 @Transactional 里 updateById → delete 缓存)。
为什么删不更:更新缓存在并发写下有乱序问题(A 先算后写覆盖 B),且缓存值往往需要复杂计算,写多读少时浪费;删除是懒加载,语义简单。
为什么先库后缓存:反过来(先删缓存后更库)的窗口里,读请求会把**旧值**重新填回缓存,脏数据存活到下一次删除;先库后缓存最坏情况是短暂旧数据,且删除失败可以靠"重删队列/延迟双删"补救。
被问延迟双删:更新前删一次、更新后延迟几百 ms 再删一次,覆盖"读请求在更新期间回填旧值"的窗口;我的场景店铺数据容忍秒级不一致,单删+短 TTL 足够。

### Q16:雪崩呢?

【答】代码里主要靠**逻辑过期热点 key 不设物理 TTL** 天然规避一类雪崩。通用手段:同类 key TTL 加随机抖动、多级缓存(本地 Caffeine+Redis)、集群高可用、熔断降级(我有自研三态熔断器,ShopController 查询挂了自动 fallback 到直接查库)。诚实说随机 TTL 没有在代码里实现,是注释里的方案对比——照实讲。

## D. 登录与会话

### Q17:为什么 token 放 Redis,不用 JWT?

【答】token 是 UUID,用户信息以 Hash 存 `login:token:{token}`,TTL 30 分钟。对比 JWT:
- **可主动失效**:JWT 签发后服务端无法作废(除非维护黑名单,那就又回到 Redis 了);Redis token 删 key 即踢下线,符合"登出/封号立即生效"的业务要求。
- **续期方便**:拦截器里 `expire` 一下就是滑动过期;JWT 要重新签发下发。
- **体积可控**:JWT payload 每次请求都带全量声明。
- JWT 的优势是无状态、跨服务校验不查存储——微服务网关场景更好。单体+需要服务端掌控会话,Redis 更合适。

### Q18:双拦截器怎么设计的?

【答】两个拦截器分工:
- **RefreshTokenInterceptor(order=0,拦截 /**)**:解析 header → `HGETALL login:token:{token}` → UserDTO 存入 `UserHolder`(ThreadLocal)→ 刷新 30 分钟 TTL。**无论如何都放行**——它只负责"有身份就带上"。
- **LoginInterceptor(order=1,只拦截需登录路径)**:只判 `UserHolder.getUser() == null`,null 返回 401。

为什么要拆:如果刷新逻辑和拦截逻辑耦合,那**免登录接口**(店铺浏览、支付回调)就不会刷新 token——用户一直在浏览店铺,token 却悄悄过期了,一去下单就 401,体验很差。拆开后所有请求都续期,只有写操作校验身份。

### Q19:ThreadLocal 有什么坑?你项目里有吗?

【答】有,而且是**真实存在的缺陷,我主动讲**:Tomcat 工作线程是池化复用的,`RefreshTokenInterceptor.afterCompletion` 里应该调 `UserHolder.removeUser()`,我的代码只在登出时清理——极端情况下线程残留上一个请求的用户信息,下一个走免登录白名单的请求可能拿到别人的身份(内存泄漏倒在其次)。根因是 ThreadLocal 的 entry 的 key 是弱引用、value 强引用,不 remove 就跟着线程一直活着。修复是 afterCompletion 一行 remove。**"我知道哪里会炸、为什么会炸、怎么修"就是这类问题的满分答案。**

## E. 其他后端亮点

### Q20:限流和熔断怎么做的?

【答】都是自定义 AOP:
- **限流 `@RateLimit`**(Guava RateLimiter 令牌桶):`ConcurrentHashMap<方法签名, RateLimiter>.computeIfAbsent`,`tryAcquire()` 非阻塞,失败反射调用同名 fallback 方法。使用点:秒杀 qps=50、支付 qps=20、发码 qps=1、登录 qps=5、搜索 qps=100(发码限流压测拦截率 90%)。单机限流,分布式要 Redis+Lua 或 Sentinel——照实说,并讲思路(令牌数放 Redis,Lua 原子扣减)。
- **熔断 `@CircuitBreaker`**(自研三态):CLOSED/OPEN/HALF_OPEN,`AtomicReference.compareAndSet` 做状态机转换,滑动窗口 60s 内失败 ≥10 次熔断 30s,HALF_OPEN 用 `AtomicBoolean probeSent` 只放行 1 个探测请求。实际用例:**ES 搜索失败 5 次自动熔断降级到 MySQL LIKE**,用户无感知。为什么不用 Sentinel:想搞懂熔断本质,自己写过才知道 Sentinel 的半开探测、滑动窗口统计在做什么。

### Q21:Feed 流为什么用推模式?滚动分页怎么回事?

【答】发布探店笔记时,**写扩散**:查所有粉丝,循环 `ZADD feed:{粉丝id} blogId score=时间戳`。读时直接读自己的收件箱,ZSet 按分数(时间)有序。推模式读快( O(logN) )写慢,适合读多写少、粉丝量普通的场景;大 V 用推拉结合(大 V 不推,读时拉)。
**滚动分页**:传统 `page/size` 分页在 Feed 有两个问题——分页过程中有新内容插入会重复/漏掉,且 ZSet 没有好的"第 N 页"语义。我用 `ZREVRANGEBYSCORE key max min LIMIT offset count` + 游标:每次返回 `(list, minTime, offset)`,下一页以 minTime 为 max、offset 跳过与 minTime 相同的时间戳个数。**时间戳当游标天然去重**。演示环境每页 2 条方便观察。

### Q22:Redis 都用了哪些结构?各自场景?

【答】一张表答完:
| 结构 | 场景 | 关键命令 |
|---|---|---|
| String | 缓存 JSON、空值防穿透、分布式锁、验证码、全局 ID | setnx/expire/incr |
| Hash | 登录用户信息(UserDTO) | hsetall/hgetall |
| Set | 一人一单判重、共同关注 | SISMEMBER/SINTER |
| ZSet | 点赞榜(时间戳排序)、Feed 收件箱、用户 pending 订单索引 | ZRANGE/ZREVRANGEBYSCORE |
| BitMap | 签到、连续签到统计 | SETBIT/BITFIELD |
| GEO | 附近店铺(按类型分 key) | GEOSEARCH 5000m |
| Stream | 秒杀削峰队列 | XADD/XREADGROUP/XCLAIM |

追问 HyperLogLog:适合海量 UV 统计(0.81% 误差、12KB 固定内存),本项目没实现,是规划项。

### Q23:ES 搜索做了什么?

【答】bool 查询:`must` 用 multi_match(name/tags/area/address 四字段,`most_fields` 提升召回)+ `filter`(typeId/area 不参与评分),ik_max_word 建索引 + ik_smart + **同义词图分词器**搜索(synonyms.txt 14 组,如"抄手/馄饨"),结果高亮。深分页保护:`from+size > 10000` 直接拒绝并提示走 search_after。ES 初始化失败不阻断启动,靠熔断器降级 MySQL LIKE——**可用性优先**。

### Q24:后端压测数字?怎么讲?

【答】(来自 perf-report.md,本机环境,讲相对量级)查询链路 100 并发 QPS 3306,P50 8.2ms / P95 17.6ms / P99 21.7ms;缓存命中平均加速 2.3 倍、冷启动 10.2 倍(DB 1.26ms vs Cache 0.54ms 是单次均值);秒杀 30 并发 QPS 803、**零超卖**;一人一单 10 并发同一用户仅 1 单成功(Lua 拦截率 90%);发码限流 qps=1 下拦截率 90%。
讲法:先说结论(零超卖、零重复),再说瓶颈在哪(单机 Redis 网络往返、Lua 串行执行的吞吐上限),再说怎么扩(Redis Cluster 分片 voucherId、消费者水平扩展按 voucherId 分组)。

## F. Agent1 快评服务

### Q25:快评的整体设计?为什么单独起一个服务?

【答】**线性五步管线**(main.py 注释里就写明"线性 Pipeline 模式,无 HITL"):
1. **采集**:httpx 调 Java REST API 拉店铺详情+分页评价,单页 10 条,**上限 250 条**。走 API 不直连 DB——数据口径与主站一致,权限、缓存都在后端收口。
2. **情感分析(每条评论)**:超过 200 条时**按点赞数采样:Top150 + 最新的 Bottom30**——高赞评论代表舆论主流,新评论代表近期变化,180 条覆盖 250 条的信息量但省 ~28% token;batch_size=5,一个 prompt 分析一批,LangChain `with_structured_output(BatchReviewAnalysis)` + `abatch` **并发批量**调用,抽取 sentiment/pros/cons/keyPhrases。
3. **统计聚合(零 LLM)**:好评率、平均点赞、`Counter.most_common` 取优缺点 Top3、关键词 Top5——**确定性计算绝不交给 LLM**,省钱且数字永远对。
4. **综合建议(LLM)**:输入统计结果,输出 100 字左右建议+评分解读。
5. **组装 JSON** 返回。

独立服务的原因:LLM 调用是**长耗时、易失败、需要限流降级**的 IO,和 Java 主链路的响应时间要求完全不同(秒级 vs 毫秒级),进程隔离 + 独立伸缩 + 故障隔离(前端 60s 超时,Java 网关不至于被拖垮)。

### Q26:LLM 输出的 JSON 不合法怎么办?

【答】`with_structured_output(Pydantic模型)`:底层是 function calling / JSON schema 约束,输出直接反序列化成 `ReviewAnalysis(sentiment: Literal["positive","neutral","negative"], pros, cons, keyPhrases)` 这样的类型,字段类型错了在 Pydantic 校验时就抛,不会污染下游。另外 temperature=0.3 压低随机性。兜底:批量失败返回 `[]`,统计环节对空结果降级为"仅基于评分和点赞的基础摘要"。(诚实补充:当前失败空结果也会写 30 分钟缓存,这是已知的待修缺陷,正确做法是失败不缓存或短 TTL——见第肆部分。)

### Q27:为什么统计用代码、建议用 LLM?边界怎么划?

【答】我的划分标准:**确定性任务(有唯一正确答案)绝不给 LLM,开放性任务(需要语言能力)才给**。好评率、Top3 缺点是算出来的,LLM 算数既贵又会错;而"把统计结果组织成一段有人味的建议"是语言任务。这个原则在 Agent2 里贯彻得更彻底:evaluate、replan 全是纯规则,LLM 只在 plan(意图→工具调用)和 generate(候选→文案)两个节点。

### Q28:Agent1 的缓存策略?数据变了怎么办?

【答】`agent1:summary:{shopId}`,TTL 30 分钟,命中直接返回(零 LLM 成本)。评论是持续写入的,快评本质是**统计快照**,30 分钟的时效折衷成本非常划算——一次快评约 180 条评论 × 每条几百 token,不打缓存每次都是真金白银。失效策略目前是被动 TTL;改进方向是评论新增/删除时后端发事件主动失效(目前没有做,照实说)。

### Q29:Agent1 和 Agent2 怎么协作?

【答】Agent2 有个工具 `get_review_summary`,内部 HTTP 调 Agent1 的 `/agent1/summary`(timeout 15s)。设计点:**失败返回空摘要而不抛异常**——Agent1 挂了,Agent2 只是少一个"好评度验证"信号,主推荐流程不阻断。这叫故障隔离/优雅降级,和后端"ES 熔断降级 MySQL"是同一个思想。

## A. 架构与选型

### Q30:为什么用 LangGraph,不用 while 循环调 LLM?

【答】推荐是**有状态的决策流**:要判断"搜完了够不够、不够要不要放宽、用户要不要追问、记不记忆",裸 while 循环把这些逻辑糊在一个函数里,不可观测、不可中断、不可恢复。LangGraph 给我三样东西:
1. **图结构**:节点+条件边,流程显式声明(我的图 8 节点 1 条四路条件边),每个节点可单独加日志/计时/评估探针;
2. **checkpointer**:状态持久化,配合 `interrupt()` 天然支持 HITL——"暂停等人回答,回来继续";
3. **以状态为中心**:State 是 TypedDict,节点只做 state→state 的纯变换,好测试(直接构造 state 断言输出,不用 mock 整个对话)。

### Q31:把你的状态图讲一遍。

【答】(画图)`load_memory → plan → execute → evaluate`,然后 evaluate 一条**四路条件边**:
- **feedback**(HITL 回来了)→ `update_memory`(LLM 从反馈提取偏好,增量合并)→ 回 `plan` 重新规划;
- **replan**(执行了预备工具但还没搜索)→ 回 `plan`(带着已有工具结果重新让 LLM 出计划);
- **relax**(候选不足)→ `replan_relax`(**纯规则**:找最近一次搜索参数,maxPrice×1.25、minScore−0.3 下限 3.0,重搜合并,新店标 `source=relaxed`)→ 回 `evaluate`;
- **generate**(够了)→ `generate`(客户端硬过滤+排序,LLM 按 R1-R8 硬规则选 Top5+matchReason)→ `log_trajectory`(轨迹落盘 Redis 30 天+入蒸馏队列)→ END。

**设计哲学:evaluate 和 replan_relax 是零 LLM 的纯规则节点**。要不要继续是确定性判断(候选数、迭代数、hitl 次数),不需要语言模型——每次省一次调用,延迟和成本降一个档,而且行为可复现、可单测。LLM 只出现在 plan(意图理解)和 generate(文案生成)两个真正需要语言能力的节点。

### Q32:HITL(人在环)具体怎么实现的?

【答】三层机制,层层兜底:
1. **图内 interrupt**:evaluate 判定候选=0 时(规则模板生成提问+4 个选项)调 LangGraph 的 `interrupt()`,抛 GraphInterrupt,线程状态存进 checkpointer,HTTP 响应返回 `type=interrupt` 载荷;前端渲染选项按钮,把 `waitingForResume` 置 true,**用户下一条消息自动走 `/agent2/chat/resume`**。
2. **Redis 快照兜底**:checkpointer 用的是 InMemorySaver——进程重启就没了。所以收到 interrupt 时我把整个 AgentState 序列化存 Redis(`agent2:interrupt:{thread_id}`,TTL 1 小时);resume 时如果 checkpointer 里没有这个线程(说明重启过),用 `Command(goto="update_memory")` **从快照直接跳进记忆更新节点**,对话体验无缝衔接。
3. **单轮守卫**:`hitl_count` 限制一轮最多 HITL 一次,防止"反复问用户就是不干活"。

被问"InMemorySaver 为什么不换 RedisSaver":学习项目进程内够用+我加了 Redis 快照兜底;生产应换持久化 saver,这是一行配置的改动(诚实+给出方案)。

### Q33:Agent 有哪些工具?怎么防止 LLM 乱调?

【答】五个工具,全部是对接真实后端或 Agent1:
| 工具 | 背后 | 用途 |
|---|---|---|
| search_shops_by_keyword | Java `/shop/search`(ES) | 细分类搜索 |
| search_shops_nearby | Java `/shop/of/type`(GEO) | 按类型+坐标泛化搜索 |
| get_shop_detail | Java `/shop/{id}` | 补详情(评分归一化) |
| get_shop_types | Java `/shop-type/list` | 拿大类 typeId |

防护:plan 节点 LLM 输出的 tool_calls 先过 `validate_tool_calls` **白名单校验**(guard.py 定义合法工具+参数 schema),不在白名单直接拒绝并记录 tool.rejected 事件;参数字符串截断 200 字;execute 自动注入用户坐标,user_id 由服务端持有不下放给 LLM。

## B. 记忆系统

### Q34:记忆分几层?各自怎么实现?

【答】三层,对应人类"工作记忆/情景记忆/经验":
1. **短期(会话级)**:MySQL `tb_agent_conversations` 存原始对话(content 截 500 字),Redis 存**压缩摘要**。关键设计:**压缩是异步 fire-and-forget**——`append_turn` 只做"写 MySQL+打 dirty 标记"就返回,`asyncio.create_task` 后台压缩(SUMMARIZE_PROMPT 压成≤12 条、每条≤50 字的 bullet),**绝不阻塞用户请求**。兜底:读路径发现缓存 miss 或 dirty,降级返回**最近 3 轮原始对话**并再踢一次后台压缩——这个叫 piggyback(顺路捎带)。
2. **中期(用户偏好,跨会话)**:9 维偏好(喜欢品类/价格区间/环境/忌口/常去商圈/特殊要求等),MySQL 为真源,Redis read-through 缓存 90 天。**增量合并**语义:列表去重追加、价格区间取更窄的交集、特殊要求覆盖——避免一次反馈覆盖全部画像。
3. **长期(全局经验 Playbook)**:跨用户共享的"经验库",见 Q35。

另一个实用细节:Redis 还存 `last_shops`(上轮推荐 Top5 的结构化信息)和 `recommended_ids`(会话内已推荐去重),支撑**"换一家更便宜的"这种指代消解**——不用 LLM 推理"一家"指谁,直接查表。

### Q35:Playbook 经验闭环是怎么跑的?

【答】这是项目最有辨识度的部分,五步闭环:**轨迹 → 信号 → 蒸馏 → 经验 → 回注**。
1. **轨迹落盘**:每次推荐结束 log_trajectory 存 TrajectoryRecord(节点日志、决策、结果)到 Redis 30 天,同时 `enqueue_for_distill` 进 ZSET 队列(24h TTL)。
2. **触发(双保险)**:**Piggyback**——用户请求入队时顺路触发一次(≥30s 节流、单轮≤4 条、时间预算 2.5s,绝不拖慢主请求)+ **Daemon**——startup 拉起后台协程每 300s 扫一批≤16 条。还有 **60s 冷却期**:轨迹落盘后至少等 60s,等用户后续交互揭示真实反馈再蒸馏。
3. **信号判定(零 LLM)**:outcome=accepted→正信号;rejected/timeout→负;**隐式接受**——outcome=unknown 但有候选且 HITL 后候选≥3,视为接受(默认大多数交互没有显式反馈,必须靠隐式信号)。
4. **蒸馏(零 LLM,纯规则反推)**:比如用户说"附近",从最终 Top5 的实际距离反推出"约 5km 范围内",学成 `trigger:"附近" → normalized:"约5km范围内"`;"便宜"→"人均 X 元以内"。**置信度反馈式更新**:同一经验再次命中,confidence 指数加权 +0.03;总量上限 200 条,超限按 `confidence×(1+times_applied×0.1)` 淘汰。
5. **回注**:下次规划时,plan 的上下文里注入命中经验(格式如 `[Playbook 规范化补全] 「附近」→约5km范围内(置信0.90)`),System Prompt 硬规则要求把它作为搜索参数约束。

**为什么蒸馏不用 LLM**:从结果反推参数是模式匹配,规则做零成本、零幻觉;LLM 蒸馏适合归纳复杂策略(我保留了一版 LLM Reflector,按 5 类规则蒸馏,但默认管线走规则版)。存储上还有个巧思:经验编码成 `[fuzzy_mapping] trigger:"X" normalized:"Y"` 文本存 description 字段,**零 schema 变更**。

**断口修复**(追问点):闭环有个隐蔽断口——轨迹蒸馏过就打 marker,但 95% 交互 outcome 是 unknown,如果用户**事后**点了"采纳/点踩",显式信号会被 marker 挡住。修法:`POST /trajectory/{id}/outcome` 更新 outcome 时**删掉 processed marker 再重新入队**,让新信号触发重判。

### Q36:经验检索为什么用向量?具体怎么做的?

【答】ChromaDB + **本地 ONNX all-MiniLM-L6-v2(384 维)embedding**——模型跑在本地进程,零 API 调用零费用,适合高频小语料检索。HNSW 余弦相似度,候选取 top_k×2,混合评分 = **相似度×0.7 + 置信度×0.3**:纯相似度会把"学过但从来没帮上忙"的条目排前面,置信度项让**被验证过的经验**优先;Chroma 挂了降级纯置信度排序。消费端匹配用户模糊词时按 trigger **长度降序**匹配,防止"店"抢了"火锅店"的前缀。

## C. 防护、观测与评估

### Q37:LLM 调用的稳定性怎么保证?

【答】`core/llm.py` 的 `call_llm` 四层防护(参数都是真实配置):
1. **令牌桶 RPM 限流**:容量=RPM(允许攒突发),填充 RPM/60 每秒,保护 API 配额;
2. **Semaphore 并发上限=2** + 队列超时 30s:防止几十个请求同时打 LLM 把内存和账单打爆,排队太久直接快速失败;
3. **指数退避重试**:最多 5 次,`min(2^(n-1), 10s)` + 0~30% jitter,**优先尊重 429 响应的 Retry-After**(上限 30s);只重试 429/5xx,4xx(参数错)重试无意义直接抛;
4. **降级**:队列超时抛 LLMBusyError,接口返回 `{"type":"busy"}`,前端提示稍后再试。
另外 openai client 的内置 `max_retries=0`——**重试逻辑必须自己接管**,否则两层重试相乘会造成雪崩式放大。

### Q38:Prompt 注入怎么防?

【答】guard.py 三层,先说做实的,再说诚实的边界:
1. **输入侧**:10+ 条中英文注入正则检测(忽略大小写/全角)、剥离 Unicode 控制字符(RLO 之类不可见字符攻击)、长度截断 500;
2. **结构隔离**:用户输入用 `<USER_INPUT>` 标签包裹,system prompt 明确声明标签内是不可信数据,工具调用必须来自白名单;
3. **输出侧**:tool_calls 白名单校验、参数截断、JSON 必要字段校验——**LLM 输出同样不可信**,它可能被诱导调用不存在的工具。

诚实边界:目前输入侧检测到注入模式只**告警不拦截**(告警进轨迹用于分析),没有做隔离推理或多 agent 审查;真正的生产方案要上输出内容审查+敏感操作二次确认。照实讲,并说明知道怎么加强。

### Q39:可观测性做了什么?

【答】双通道日志:普通文本日志(RotatingFileHandler 20MB×5)+ **workflow.jsonl 结构化事件流**(每事件一行 JSON,50MB×5)。`contextvars` 维护 requestId/threadId/trajectoryId/userId 全链路关联(HTTP 中间件生成 uuid,响应头回传 `X-Agent2-Request-Id`)。事件覆盖 request.received/completed、llm.started/retry_scheduled/failed(含 tokenUsage)、tool.started/rejected、node.started/interrupted、graph.routed、distill.* 全链路。安全:敏感 key(api_key/token/password)脱敏、payload 截 4000 字、写日志失败静默——**观测本身绝不能弄挂推荐请求**。

### Q40:评估怎么做?消融实验有什么发现?

【答】(数字来自 agent2_test_report.md,全部真实)
**评估集**:60 条单轮用例(6 品类 × 单/双/三重约束,含拼音容错如 kvt/hguo)+ 20 个多轮场景(指代消解/偏好修正/逐步细化/HITL 恢复/跨轮拼写容错,各 3-5 轮)。
**指标**:passRate、CSR(品类+价格+评分+距离同时满足)、HITL 必要/过度率、LLM-as-Judge 三维(relevance/diversity/reasoning 1-5 分)、Trajectory Judge 五维(intent 理解/工具选择/调用顺序/反思利用/终止时机)、token 用量与 P50/P95 延迟。
**消融**(关掉某个模块对比):`-Memory` 使火锅/足疗场景退化为 HITL 或零推荐(记忆承载跨轮约束);**`-Playbook` 反直觉地让部分指标变好**(KTV/足疗从 HITL 变为有推荐,relevance +3.3)——归因是早期 Playbook 条目噪声大、过度保守,为此加了 `PLAYBOOK_MIN_NOVELTY=0.5` 的准入门槛和置信度加权淘汰。**这个"负结果"是我最喜欢的实验**:自进化系统会学坏,必须有质量门。

## 3.1 Redis

### Q1:Redis 为什么快?

【答】①纯内存;②单线程无锁无上下文切换(命令执行线程);③IO 多路复用(epoll)非阻塞处理海量连接;④高效数据结构(SDS 预分配、跳表、压缩列表 listpack)。Redis 6+ 网络 IO 是多线程的,命令执行仍单线程——所以 Lua 脚本里的慢操作会阻塞一切(我的 seckill.lua 全 O(1) 命令就是为此)。

### Q2:ZSet 底层?为什么用跳表不用红黑树?

【答】ziplist/listpack(小数据)→ skiplist + dict 双结构。跳表:范围查询 ZRANGE 天然有序 O(logN);实现简单(插入删除不用旋转);按排名操作方便(跨度 span)。红黑树范围查询要中序遍历,实现复杂。我的 Feed 收件箱、点赞榜、用户 pending 订单索引全靠它的 score 有序+范围取。

### Q3:Redis 持久化?

【答】RDB:定时快照,fork 子进程写,恢复快、文件小,但两次快照间丢数据。AOF:追加写命令,appendfsync everysec 折衷,丢 1 秒;重写压缩(bgrewriteaof)。4.0+ 混合持久化(重写时全量 RDB+增量 AOF)。我的场景:秒杀库存/订单在 Stream+DB 有完整副本,Redis 数据可重建,默认配置即可;交易状态真源在 MySQL。

### Q4:过期删除和内存淘汰?

【答】删除:惰性(访问时查)+定期(每 100ms 随机抽样)。淘汰:noeviction(默认)/ allkeys-lru / volatile-lru / allkeys-lfu 等。项目挂钩:登录 token 30 分钟、验证码 2 分钟、预订单 10 分钟、Agent 会话 24h——TTL 是我主要的"状态生命周期管理工具"。

### Q5:缓存穿透/击穿/雪崩(通用版)

【答】穿透(查不存在的 key):空值缓存(我用的)/布隆过滤器/接口层参数校验。击穿(热点 key 过期):互斥锁重建/逻辑过期不设物理 TTL(我实现的)/热点永不过期。雪崩(大面积同时过期):TTL 加随机/多级缓存/集群 HA/限流熔断兜底。答完通用版立刻接"我的项目里分别是:空值 2 分钟、逻辑过期+setnx 抢锁异步重建返回旧值、雪崩主要靠逻辑过期天然规避+熔断降级"。

### Q6:Redis 分布式锁的演进?

【答】v1 `setnx`+`expire` 两步——中间崩溃死锁;v2 `set key value nx ex` 原子加锁——但会**误删别人的锁**(超时后别人拿到了);v3 value 存"线程标识",释放时**Lua 判断值相等再删**(我的 SimpleRedisLock);v4 Redisson:看门狗自动续期+可重入(Hash);v5 RedLock 多数派——有时钟争议,多数场景"单实例+业务幂等兜底"够用。我消费端就是 Redisson 阻塞锁+watchdog,粒度 userId+voucherId。

### Q7:Redis 6.0 为什么引入多线程?

【答】瓶颈不在命令执行而在网络 IO(读写 syscall、协议解析)。6.0 IO 线程并行处理读写和协议解析,命令执行仍单线程保原子性。所以"Redis 单线程"指命令执行。

### Q8:大 key / 热 key?

【答】大 key(value 巨大或元素过多):删除阻塞(用 UNLINK/SCAN 渐进)、网络放大、集群倾斜;发现(redis-cli --bigkeys)拆分。热 key:单分片 CPU 打满;本地缓存兜底、key 加随机后缀打散读。我的预防:INCR 的 key 按天分片;feed 按 userId 分 key 天然打散。

### Q9:Redis Stream vs Kafka/RabbitMQ?

【答】Stream:Redis 内置,消费者组+ack+pending 重投+XCLAIM 故障转移,轻量、与业务数据同实例零额外运维,吞吐受 Redis 单机限制,消息量受内存约束——**我的秒杀削峰选它是因为预扣本来就在 Redis 里,Lua 内 XADD 一次网络往返**。Kafka:分区顺序、超高吞吐、磁盘顺序写、重放强,但运维重。RabbitMQ:路由灵活(Topic/DLX)、低延迟,吞吐中等——我的延迟取消用它的死信队列。没有银弹,按"量级+是否已有设施+延迟语义"选。

## 3.2 MySQL

### Q1:为什么用 B+ 树?

【答】对比:Hash 等值快但不支持范围;二叉/红黑树树高随数据量增长(IO 次数=树高);B 树非叶节点也存数据导致扇出小。B+ 树:非叶节点只存索引(扇出大,千万数据 3~4 层)、叶子双向链表(范围查询/排序友好)、所有查询都要到叶子(稳定)。我的 `idx_user_status_time(user_id,status,create_time)` 支撑"我的订单按状态+时间查"就是链表范围扫。

### Q2:聚簇索引、回表、覆盖索引?

【答】聚簇=叶子存整行(InnoDB 主键);二级索引叶子存主键值,查询非索引列要**回表**。覆盖索引=查询列全在索引里免回表。项目挂钩:一人一单 count 走 `idx_user_voucher_status(user_id,voucher_id,status)`,如果只 count 就不回表;秒杀判重能走 Redis 就不碰 DB——让索引层挡在最前面。

### Q3:最左前缀与索引失效?

【答】联合索引 (a,b,c):查询条件必须从 a 开始连续;范围查询后面的列失效(a=1 and b>2 则 c 不参与)。失效场景:函数/运算作用于索引列、隐式类型转换(字符串列传数字)、前导模糊 like '%x'、or 两侧非全索引。项目里我的订单查询严格按 (user_id, status, create_time) 顺序构造条件。

### Q4:事务隔离级别与 MVCC?

【答】读未提交(脏读)/读已提交(不可重复读)/可重复读(InnoDB 默认,幻读基本防住)/串行化。MVCC:每行隐藏 trx_id、roll_pointer 版本链 + ReadView(活跃事务列表)判断可见性;RC 每次查询新建 ReadView,RR 事务内复用第一个。快照读走 MVCC 无锁,当前读(SELECT FOR UPDATE / UPDATE)读最新版并加锁——我支付时 `selectByIdForUpdate` 就是当前读,必须拿到订单最新状态再条件更新,防"查的时候还能付,更新的时候已被取消"。

### Q5:InnoDB 锁?

【答】行锁(记录锁/间隙锁/临键锁 Next-Key=记录+间隙,RR 级别防幻读)、表锁、意向锁、MDL。死锁:互相等待,InnoDB 检测回滚代价小的事务。项目经验:`selectByIdForUpdate` 锁行要确认走索引(不走索引锁全表);我的更新全是"条件 UPDATE"本身加行锁,天然互斥。

### Q6:唯一索引做幂等的原理?和"先查再插"的区别?

【答】`uk_active_user_voucher` 让并发下的重复插入在**存储层**串行化:后到者阻塞或抛 DuplicateKey。"先 select 再 insert"在两个请求都通过 select 后同时 insert,仍会重复(除非加锁);唯一索引是最终真相,我捕获 DuplicateKeyException 转业务语义。代价:插入失败有锁开销,高频冲突场景要先挡一层(Redis SISMEMBER)。

### Q7:深分页问题?

【答】`LIMIT 1000000, 10` 要扫过前 100 万行。优化:游标/续传式分页(`where id > last_id limit 10`,我 Feed 滚动分页就是这个思想的时间戳版)、延迟关联(先查主键再回表)、ES search_after(我在 ES 里 from+size>10000 拒绝并提示 search_after)。我的 GEO 附近店铺用 `limit(end)` 取回前 N 页再截取,深分页时会多取——已知待优化点,诚实讲。

### Q8:分库分表?

【答】垂直(按业务拆库/大字段拆表)、水平(按 shard key 哈希/范围)。带来的问题:分布式事务(TCC/消息最终一致——我的 Outbox 就是最终一致的落地)、跨片查询、全局 ID(我的 RedisIdWorker 就为此设计)、扩容(一致性哈希/翻倍迁移)。什么时候拆:单表千万级、写入成为瓶颈再拆,不提前。

## 3.3 并发编程(JUC)

### Q1:线程池七参数与执行流程?

【答】corePoolSize、maximumPoolSize、keepAliveTime+unit、workQueue、threadFactory、handler。流程:核心线程→队列→非核心线程→拒绝策略(Abort/CallerRuns/Discard/DiscardOldest)。项目挂钩:缓存重建 `newFixedThreadPool(10)`(固定 10=core=max,无界队列 LinkedBlockingQueue——主动讲隐患:队列无界可能 OOM,应换有界+自定义拒绝);秒杀消费者 `newSingleThreadExecutor`(单线程保证落库顺序,daemon 不阻 JVM 退出)。为什么不用 Executors 静态方法:阿里规约——Fixed/Single 队列无界,Cached 最大线程无界。

### Q2:ThreadLocal 原理与内存泄漏?

【答】每个 Thread 持 ThreadLocalMap,key 为 ThreadLocal 弱引用,value 强引用。GC 后 key 为 null 但 value 还在,线程池线程不死就泄漏。所以用完必须 remove。我的真实案例:UserHolder 在 afterCompletion 没 remove(见 Q19),线程复用还可能串号——**这题我有一手素材**。

### Q3:CAS 与 AQS?

【答】CAS:cmpxchg 硬件指令,三个操作数(内存值/期望/新值),问题 ABA(版本号 AtomicStampedReference 解决)、自旋开销、只能单变量。我的自研熔断器用 `AtomicReference.compareAndSet` 做状态迁移(CLOSED→OPEN→HALF_OPEN),HALF_OPEN 用 AtomicBoolean 保证只放一个探测请求。AQS:volatile state + CLH 双向队列 + 独占/共享模式,ReentrantLock/Semaphore/CountDownLatch 底座;我的 LLM 并发防护用的 Semaphore(2) acquire 超时放弃,就是 AQS 共享模式。

### Q4:synchronized 与 ReentrantLock?锁升级?

【答】synchronized 偏向锁→轻量级(自旋+CAS)→重量级(monitorenter);ReentrantLock 可中断/超时/公平/多条件变量。项目选择:消费端 Redisson lock() 是**分布式**锁,与 JVM 锁不是一个层面——单机内用 JVM 锁,跨进程互斥必须分布式锁。

### Q5:volatile?

【答】可见性(MESI 缓存一致性+内存屏障)+禁止指令重排,不保证原子性。双重检查单例必加。追问 happens-before:程序顺序/监视器锁/volatile/线程 start-join/传递性。

## 3.4 Spring

### Q1:IOC/AOP 理解?

【答】IOC:对象创建和依赖装配交给容器,业务代码面向接口。AOP:动态代理(JDK 接口代理/CGLIB 子类)织入横切逻辑。我的项目里 AOP 是**生产力工具**:`@RateLimit`(限流)、`@CircuitBreaker`(熔断)两个自定义注解+切面,业务方法一行注解获得防护——这就是 AOP 的价值示范。

### Q2:Bean 生命周期?

【答】实例化→属性注入→Aware 回调→BeanPostProcessor.before→初始化(InitializingBean/init-method)→after(代理一般在这生成)→使用→销毁。单例默认随容器启动(可 @Lazy 延迟)。

### Q3:循环依赖三级缓存?

【答】一级 singletonObjects 成品、二级 earlySingletonObjects 提前暴露、三级 singletonFactories 工厂(为的是按需生成代理)。A 创建中暴露工厂→B 注入 A 的早期引用→B 完成→A 继续。构造器注入解决不了(还没到暴露阶段)。我的项目:PaymentServiceImpl ↔ VoucherOrderServiceImpl 互相依赖,**双向 @Lazy 打破**——注入的是代理,首次调用才触发真实初始化。另外我故意用 `@Lazy` 自注入拿到**自身代理**解决事务自调用失效(Q12),对三级缓存的理解就来自这个实操。

### Q4:事务传播行为?@Transactional 失效场景?

【答】常用:REQUIRED(默认,合并)、REQUIRES_NEW(独立)、NESTED(保存点)。失效:自调用(this)、方法非 public、异常被 catch、默认只回滚 RuntimeException/Error(受检异常要 rollbackFor)、多线程(事务绑定 ThreadLocal 连接)。我的实操:消费线程里 this 调用事务方法失效→@Lazy 自注入代理(真实踩坑,细节见 Q12)。

### Q5:拦截器 vs 过滤器 vs AOP?

【答】Filter(Servlet 规范,最外层,能改请求响应流)、Interceptor(Spring MVC,Handler 前后,能拿 Handler 信息)、AOP(方法级,最细)。我的分层实践:登录态用拦截器(需要知道路由信息+刷新 token),限流熔断用 AOP(作用在 service 方法,与 HTTP 无关),跨域/编码用 Filter。

## 3.5 消息队列

### Q1:消息不丢的全链路?

【答】生产端:confirm(我同步等 ack 5s)+ Outbox 兜底重发;broker:交换机/队列/消息持久化+镜像/仲裁队列;消费端:手动 ack,异常 nack 重投。我的落地:Outbox 表(publisher-confirm 失败→指数退避重发)+ Stream PENDING/XCLAIM,见 Q7。

### Q2:重复消费怎么办?

【答】必然发生(重投/确认丢失),消费端幂等是唯一解:唯一键约束(我的 uk_active_user_voucher)、状态机条件更新、业务前置存在性检查(先按 orderId 查)、Redis setnx 去重标记。我的消费者四重幂等见 Q3/Q10。

### Q3:延迟消息几种实现?

【答】RabbitMQ 死信队列(TTL 到期转 DLX,我用的;缺点:队列头阻塞——RabbitMQ 检查队首,前面消息 TTL 长会挡住后面的,所以我的延迟统一 30 分钟+消息级 TTL 按剩余时间动态调)、延迟插件(rabbitmq_delayed_message_exchange)、Redis ZSet 轮询、时间轮(Netty HashedWheelTimer,海量高精度)。我的选型理由+队首阻塞这个坑能讲出来就是加分项。

## 3.6 网络

### Q1:TCP 三次握手/四次挥手?

【答】三次:SYN→SYN+ACK→ACK,为什么三次:双方都确认收发能力,防历史重复连接(SYN 洪水攻击→SYN Cookie)。四次挥手:FIN→ACK→FIN→ACK,TIME_WAIT 2MSL:确保最后 ACK 送达+让旧连接报文自然死亡。可以挂:httpx 长连接复用(连接池)减少握手。

### Q2:HTTPS 握手?和你的 HMAC 验签什么关系?

【答】TLS:非对称协商对称密钥,之后对称加密。数字证书解决公钥信任(CA 链)。HMAC 是另一层:**传输加密≠身份认证**,TLS 保证"没人窃听篡改这条链路",HMAC 保证"这个回调确实是持有 secret 的支付平台发的"——双重防护,且我的比较用常量时间函数防时序侧信道。

### Q3:从输入 URL 到页面展示?

【答】DNS(浏览器/系统/运营商缓存迭代查询)→TCP/TLS→HTTP(keep-alive 复用)→服务端(Vite 代理转发→Nginx 生产)→渲染(解析 DOM/CSSOM→布局→绘制)。可以顺势讲我的 Vite 代理把 /agent1 /agent2 转发到本地服务,生产应换 Nginx/网关。

## 3.7 操作系统

### Q1:进程/线程/协程?

【答】进程资源分配单位(独立地址空间),线程调度单位(共享进程资源),协程用户态调度(切换无需内核介入)。**我的实战**:FastAPI+asyncio 单线程事件循环跑协程——并发来自 IO 重叠(等 LLM/Redis 时切换),CPU 密集会卡整个循环(所以同步 Redis 客户端是我的已知缺陷,应换 redis.asyncio);Java 侧线程池+阻塞 IO 是另一种模型(线程等待)。两套都写过,能对比。

### Q2:IO 多路复用?

【答】select(1024 限制+全量扫描)/poll(无限制仍 O(n))/epoll(红黑树注册+就绪链表回调,O(1),LT/ET 模式)。Redis、Nginx、Netty 的基石。挂 Redis 单线程+epoll 处理十万连接(见 3.1 Q1)。

### Q3:零拷贝?

【答】传统 read+write 4 次拷贝 4 次切换;mmap 减一次;sendfile DMA 直达 2 次。Kafka 高吞吐的根基之一(顺带 MQ 选型话题)。

## 4.1 "你的项目有什么不足?"(必被问,背熟)

标准框架:**主动承认具体缺陷 → 分析根因 → 给出已验证的修复方向**,忌讳说"没啥不足"。

> 最大的不足有三类。**安全工程上**:拦截器白名单放得太宽(/voucher/**、/shop/** 把写操作也放行了)、密码哈希用的 MD5+盐(应该 BCrypt)、Agent 服务的调试接口(eval/trajectory)没有鉴权、userId 由前端传入可伪造——这是我系统学习安全清单后 review 出来的,修复方案都很明确(白名单收窄到 GET、换 BCrypt、Agent 网关加 token 鉴权、服务端解析身份),但还没来得及全部落地。
> **代码质量上**:CacheClient 逻辑过期分支 unLock 传错了 key、Agent1 会把 LLM 失败的空结果缓存 30 分钟、快评前端没处理 busy 分支——这些是靠 code review 和测试报告自己发现的,每一个我都能说清触发条件和影响面。
> **架构上**:Agent2 的 checkpointer 是 InMemorySaver(重启丢中断状态,我用 Redis 快照+Command(goto) 打了补丁,但正解是持久化 saver);async 路径里用了同步 Redis 客户端,会阻塞事件循环;Python 直连业务库(shop_api_mysql)绕过了 Java 缓存层,数据通道有双份风险。

这样答的信号:你能**自己发现**问题、能评估**影响面**、知道**正解**——校招这就够了。

## 4.4 高频场景设计题(带项目素材的答法)

**Q:秒杀扩到 100w QPS?**
A:垂直拆:静态资源 CDN→网关层限流(令牌桶我有了,升分布式 Redis+Lua)→库存分片(按 voucherId 哈希到多个 Redis 片,每片独立 Lua)→本地缓存预售标记(售罄后本地直接拒,不打 Redis)→MQ 削峰(已有 Stream,可换 Kafka)→DB 唯一索引兜底(已有)。核心理念:**每一层都让更少的请求到达下一层**,我的五层结构已经是这个思想的缩小版。

**Q:热点 key 打爆某个分片?**
A:本地缓存(Caffeine)多副本+key 打散读+逻辑过期(我已实现)让热点 key 永不物理过期。

**Q:Agent 成本怎么控制?**
A:分层:确定性逻辑零 LLM(我的 evaluate/replan/统计/蒸馏已实现)→缓存(快评 30min、偏好 90d)→采样(top150+bottom30)→上下文预算(每请求 30k token 上限、会话截 1500 字、候选截 10 家)→并发+RPM 限流防失控→token 用量按 request 统计进 jsonl,可核算到每次对话。

**Q:怎么防止 LLM 给出错误推荐?**
A:信任分层:LLM 负责"理解和表达",**决策约束在代码里**——工具白名单、客户端硬过滤(R1-R8 规则过滤价格/评分/排除词)、排序规则代码做,LLM 只在过滤后的候选里选;轨迹全量落盘可回溯;评估集回归。
